## Блок 2. Приоритет P0 (Критично к хакатону: Zero-Mock, Скорость и Web UX)

### 2.1. Устранение узких мест производительности и блокировок
1. **Предзагрузка (Warmup) BGE-M3 при старте сервера (`lifespan` в `backend/main.py`):**
   - Сейчас `SentenceTransformer("BAAI/bge-m3")` инициализируется лениво при первом запросе студента (`vector_store.py:37`), вызывая **фриз первого ответа на 10–25 секунд**.
   - **Решение:** прогревать модель и прогонять тестовый вектор `model.encode(["warmup"])` на этапе старта контейнера/приложения + вынести все вызовы `vector_store.search_relevant_slides` и `vector_store.add_slides` в `await asyncio.to_thread(...)`, чтобы CPU-инференс PyTorch никогда не блокировал event loop FastAPI.
2. **Стриминг сократического диалога (SSE) + Развязка 3-го шага и Аудита (`backend/main.py`, `backend/llm_service.py`):**
   - **Узкое место сейчас:** на 3-м шаге `POST /api/v1/dialog/turn` делает **два последовательных LLM-вызова** (ответ тьютора + тяжелая экстракция `extract_audit_evidence` на 3000 токенов), заставляя студента смотреть на зависшую кнопку `Думает...` до 12–15 секунд.
   - **Решение:**
     - Добавить потоковый эндпоинт `POST /api/v1/dialog/turn/stream` (Server-Sent Events): первые токены ответа тьютора появляются на экране уже через **300–600 мс** с плавной анимацией набора.
     - После завершения стрима 3-й реплики сессия сразу переходит в статус `AUDITING`, студент мгновенно получает благодарность за рефлексию, а Слой 3A/3B (`extract_audit_evidence` → верификация `K_density` по глоссарию БД → `ThemisMathEngine` → запись в SQLite) выполняется в `BackgroundTasks` (2–4 сек) с push-уведомлением в консоль преподавателя через легковесный SSE-канал `/api/v1/events/audit-stream`!

```
 │    ├── POST /api/v1/dialog/turn/stream (SSE)
 │    └── POST /api/v1/session/opt-out
       │
       ▼ (SSE push после 3-го шага)
[Большой экран на сцене: Web-консоль преподавателя]
```

#### 1. Схема авторизации, валидации `initData` и связки `telegram_id` ↔ `student_id`
- **Модуль `backend/tma_auth.py`:**
  1. Клиент TMA передает сырую строку `window.Telegram.WebApp.initData` в заголовке `Authorization: tma <initData>`.
  2. Бэкенд парсит query-параметры, извлекает `hash`, сортирует остальные пары `key=value` по алфавиту через `\n` (`data_check_string`).
  3. Вычисляет `secret_key = HMAC_SHA256(key=b"WebAppData", msg=TELEGRAM_BOT_TOKEN.encode())` и сверяет `HMAC_SHA256(secret_key, data_check_string)` с `hash` через `hmac.compare_digest`, а также проверяет свежесть `auth_date` (TTL 24 часа).
- **Связка `telegram_id` ↔ `student_id` в SQLite (новая таблица `student_identities`):**
  - Поля: `student_id PRIMARY KEY`, `telegram_id INTEGER UNIQUE NULL`, `telegram_username TEXT`, `display_name TEXT`, `group_id TEXT`, `default_grade REAL DEFAULT 75.0`, `created_at TIMESTAMP`.
  - **Два бесшовных сценария входа:**
    1. **Боевой / Гостевой вход на хакатоне (Zero-Friction для жюри):** если `telegram_id` впервые открывает TMA по ссылке курса/QR-коду (`t.me/<bot>?startapp=pai_week_09`), бэкенд автоматически создает персональную запись `stud_tg_<telegram_id>` с именем из профиля Telegram (`first_name + last_name`) и стартовой очной оценкой (или привязкой по 4-значному пин-коду ведомости студента, если он уже есть в `group_1`). Член жюри проходит 3 шага с телефона — и **его настоящее имя и точка мгновенно появляются на проекторе в Консоли преподавателя!**
    2. **Привязка к существующему студенту ведомости:** ввод одноразового кода привязки из консоли преподавателя (`link_code`) связывает существующий `stud_aai_XXX` с `telegram_id`.
- **Минимальный Bot Webhook / Long-Polling (`backend/telegram_bot.py`):**
  - Обрабатывает команду `/start [payload]` через `httpx` к Telegram Bot API (даже без лишних тяжелых фреймворков!) и отправляет приветственную карточку инклюзивного пандуса с кнопкой `WebAppInfo(url=f"{PUBLIC_APP_URL}/tma")` + в Консоль преподавателя добавляется кнопка **«📱 QR-код для входа группы в TMA»**.

#### 2. Переиспользование API без дублирования бизнес-логики
- Никаких отдельных `/api/tma/turn` роутов с копипастой логики!
- Создается единая зависимость FastAPI `Depends(resolve_student_context)`:
  - Если запрос пришел с валидным заголовком `Authorization: tma ...`, `student_id` берется строго из криптографически подтвержденного `telegram_id` (студент в TMA физически не может подделать чужой `student_id`).
  - Если запрос пришел из демо-режима Web SPA (`SCHEDULE_FORCE_OPEN` / `DEMO_WEB_AUTH`), используется выбранный `student_id`.
- Все эндпоинты (`/api/v1/session/start`, `/api/v1/dialog/turn/stream`, `/api/v1/session/active/me`, `/api/v1/syllabus/weeks`) обслуживают и Web, и TMA идентично.

#### 3. Мобильный UX для TMA (`frontend/tma.html` — отдельный чистый mobile-first интерфейс)
- **Защита от случайного закрытия:** вызов `Telegram.WebApp.expand()` и `Telegram.WebApp.enableClosingConfirmation()` при активной незавершенной сессии (Шаги 1–2), чтобы случайный свайп вниз не оборвал мысль студента.
- **Работа с мобильной клавиатурой (`visualViewport` API):** фиксация контейнера через `100dvh` и слушатель `window.visualViewport.addEventListener('resize', ...)`, автоматически прокручивающий последнюю реплику тьютора над полем ввода при поднятии клавиатуры на iOS/Android + авто-высота `textarea`.
- **Компактный мобильный хедер:** синхронизированный с сервером таймер окна (`⏱ 42:15`), 3-точечный индикатор прогресса шагов (`● ● ○ Шаг 2 из 3`), тактильный отклик `Telegram.WebApp.HapticFeedback.notificationOccurred('success' | 'warning')` при переходе на следующий уровень SOLO или срабатывании анти-спам фильтра.
- **Психологическая безопасность (UDL):** в мобильном приложении студента намеренно скрыты технические метрики ($Z$-score, вероятности $p_1, p_2, p_3$, сырой индекс) — студент видит только спокойный поддерживающий диалог, глоссарий-подсказку темы и явное уведомление, что его очная оценка в безопасности.

### 3.2. Модульная загрузка курсов (Zero-Config Ingestion Pipeline)

Цель — реализовать принцип **«Загрузил материалы любого курса → база знаний, силлабус, глоссарий и HNSW-индекс организовались сами в фоне без перезапуска»**.

```
[Файлы: PDF / PPTX / DOCX / IPYNB / MD / ZIP]
       │  POST /api/v1/courses/{course_id}/ingest (Background Job)
       ▼
[1. DocumentToMarkdownConverter] ──► Чистые структурированные .md файлы
       │                             (заголовки #..###, таблицы GFM, код, LaTeX)
       │                             data/courses/{course_id}/topics/{topic_id}.md
       ▼
[2. CourseAutoStructurer (LLM + Fallback)]
       ├── Выделение тем/модулей и метаданных курса
       ├── Генерация сократического initial_prompt + 3 demo_turns
       └── Извлечение доменного глоссария (RU/EN термины) ──► SQLite (lecture_glossary)
       ▼
[3. SemanticMarkdownChunker + BGE-M3 Worker (ThreadPool)]
       ├── Чанкинг по секциям без разрыва таблиц/кода/формул + Breadcrumb контекста
       ├── Батч-эмбеддинги BAAI/bge-m3 (1024-dim)
       └── Инкрементальный Upsert в ChromaDB HNSW (фильтр course_id + topic_id)
```

#### Этап 1. Прием и конвертация в чистый `.md` (`backend/markdown_converter.py`)
- **Поддерживаемые форматы:** `.pdf` (`pypdf` / структурная очистка), `.pptx` (`python-pptx`: заголовки слайдов → `##`, списки → `-`, таблицы → GFM `|...|`), `.docx` (`python-docx`: стили `Heading 1..3` → `#..###`, таблицы, списки, формулы OMML/текст), `.ipynb` (markdown + очищенные `python` code-блоки без base64-картинок), `.md`/`.txt`, а также `.zip`-архив целого курса.
- **ИИ-нормализация разметки (Hybrid Cleanup):** для «сложных» документов (PDF после верстки с разорванными переносами, склеенными таблицами и формулами) конвертер прогоняет грязные текстовые блоки через быстрый структурный промпт LLM (`temperature=0.0`), преобразующий сырой текст в валидный Markdown с сохранением всех заголовков `#`, списков, LaTeX-формул `$...$` и таблиц без сокращения текста. При недоступности LLM работает детерминированный парсер форматирования.
- Все результаты сохраняются как физические `.md`-файлы с YAML-frontmatter в `data/courses/{course_id}/{topic_id}.md`.

#### Этап 2. Авто-структурирование и глоссарий для `K_density` (`backend/ingestion_service.py`)
- Если преподаватель загрузил один или несколько файлов без ручного заполнения полей («Zero-Config»):
  1. Система анализирует оглавление (`#` / `##` заголовки `.md`) и автоматически определяет название курса/модулей (`topic_id`, `week_number`, `topic_name`).
  2. Через один Structured JSON-запрос к LLM (по саммари разделов `.md`) генерируются:
     - `initial_prompt` — проблемный стартовый сократический вопрос по материалу лекции;
     - `glossary` — 15–30 точных доменных терминов и их нормализованных форм (RU + EN), которые записываются в таблицу `lecture_glossary`;
     - `demo_turns` — 3 примера реплик (SOLO 1, 2, 3) специально для быстрого тестирования нового курса в Dev Mode.
  3. **Связка с детерминированным расчетом `K_density`:** при аудите диалога `ThemisMathEngine` сопоставляет концепты из ответа студента и `extraction.mastered_concepts` со словарем `lecture_glossary` конкретного `(course_id, topic_id)` (через стемминг из `similarity_service`), исключая галлюцинации терминов со стороны LLM.

#### Этап 3. Семантический чанкинг и инкрементальная HNSW-индексация в фоне
- **Семантический чанкер (перенос и развитие `smart_chunk_markdown` в `backend/chunker.py`):**
  - Делит `.md` иерархически по заголовкам `#` → `##` → `###`;
  - Атомарно защищает блоки ```` ```...``` ````, таблицы `|...|` и формулы `$$...$$` от разрезания посередине;
  - В начало каждого чанка инжектирует хлебные крошки: `[Курс: {course_title} | Тема: {topic_name} | Раздел: {section_heading}]`, что радикально повышает точность плотного поиска `BAAI/bge-m3`.
- **Фоновый пайплайн без рестарта (`ingestion_jobs`):**
  - Загрузка возвращает `202 Accepted` с `job_id`.
  - В фоновом пуле потоков батчами считаются эмбеддинги `BGE-M3` и выполняется **селективный `upsert`** в HNSW-коллекцию ChromaDB (`ids = f"{course_id}__{topic_id}__c{idx:04d}"`, перед этим удаляются старые чанки **только этой пары `(course_id, topic_id)`**).
  - В модальном окне загрузки Web UI отображается **реальный прогресс по этапам** (`Конвертация в .md` → `Извлечение тем и глоссария` → `Векторизация BGE-M3: чанк 42/68` → `Готово!`).

#### Модульная изоляция данных по `course_id` / `topic_id`
- **SQLite схема:**
  - `courses (course_id PRIMARY KEY, title, instructor, description, created_at)`
  - `syllabus_weeks (course_id, topic_id, week_number, title, topic_name, initial_prompt, demo_turns_json, md_path, chunks_count, PRIMARY KEY (course_id, topic_id))`
  - `lecture_glossary (course_id, topic_id, term, PRIMARY KEY (course_id, topic_id, term))`
  - `student_audits (student_id, course_id, topic_id, ..., telemetry_clean, teacher_decision, PRIMARY KEY (student_id, course_id, topic_id))`
- **ChromaDB HNSW:** единый загруженный в память экземпляр `BAAI/bge-m3` обслуживает все курсы без лишнего расхода RAM, а строгая изоляция на уровне метаданных `where={"$and": [{"course_id": course_id}, {"topic_id": topic_id}]}` гарантирует нулевое смешивание контекстов между разными дисциплинами и неделями.
